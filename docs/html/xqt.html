XQT 压缩与部署阅读页

这是 xqt/ 的阅读版入口. 它不替代 docs/md/XQT.md 的规划文档, 也不替代源码; 它的目标是让人更快看懂 XQT 现在到底在做什么, 为什么会有这些模块, 一条 recipe 是怎么跑起来的, 以及哪些函数和类值得直接上手.

事实边界以源码和 docs/md 为准. 当前 XQT 仍是实验包, 只有顶层入口和 XDL adapter 被列为 Provisional API, 子模块细节仍按 Internal 处理.

一. XQT 在干嘛

先不要把它理解成一个“大而全的新框架”. 现在更准确的说法是: 它是 XDL 仓库里一条独立的模型压缩与部署工具链, 负责把训练产物继续往量化, 剪枝, 蒸馏, 导出和验证那一段推进.

输入是什么

主要输入是 PyTorch nn.Module, checkpoint, 以及一份用 OmegaConf 加载的 YAML recipe. 如果你已经有 XDL 的 TrainSetup 或训练出来的 checkpoint, 也可以通过 adapter 接进来.

输出是什么

输出是变换后的模型, 导出产物, 指标报告和 manifest. 典型产物包括 .onnx, TensorRT engine, .pt2, .pte, 以及 metrics.json, metrics.md, manifest.json.

它不做什么

它不替代 xdl.trainer.Trainer, 不重新实现 TensorRT 或 ONNX Runtime, 也不承诺目前每个子模块都已经稳定. 现在最可靠的是“recipe 驱动的最小闭环”, 而不是某个内部 helper 的长期兼容性.

二. 它是怎么来的

XQT 不是先画完架构图再从零实现的. 从当前仓库能看出来, 它是先从几类专题实验脚本长出来, 然后逐步收敛成包结构.

来源 今天在 XQT 里的痕迹 说明
xqt/torchao_vit.py xqt.quant.torchao_backend, xqt.quant.sensitivity, xqt.benchmark.latency 最早是 ViT + torchao FP8 实验, 里面已经有“选择量化哪些层”“逐层误差分析”“跑性能基准”这些核心想法. 现在这些能力被拆成了更通用的量化和 benchmark helper.
扩散推理实验脚本 xqt.diffusion_distill 当前仓库里已经开始收拢 timestep schedule, latent/cache, consistency 风格 loss 和采样报告对象, 但它还明显处在“给少步蒸馏铺路”的阶段.
部署研究资料和 smoke 需求 xqt.export, xqt.pipeline, xqt.recipes 为了把 ONNX, TensorRT, ExecuTorch, ncnn, MNN 这些路径从零散实验变成可复跑闭环, 仓库把它们抽成了统一 export adapter 和 recipe runner.
XDL 训练生态 xqt.xdl_adapter XQT 没有自己再造一套训练配置生态, 而是提供 xdl_setup_to_xqt_context 和 checkpoint loader, 让训练结果直接继续接压缩与部署流程.

所以阅读 XQT 时最重要的心理预期是: 这是“从真实实验反推出来的工程工具链”, 不是“所有方向都已经抽象到位的成品包”. 这也是为什么顶层 API 已经有了, 但很多内部模块仍不承诺稳定.

三. 最值得先记住的三个入口

如果你只是想知道“我该从哪里开始用”, 优先记住这三个入口就够了.

CLI

xqt-run-recipe

读取环境变量 XQT_CONFIG, 默认跑 xqt/recipes/smoke_cpu.yaml. 它不解析命令行参数, 配置切换完全靠 YAML 或环境变量.

XQT_CONFIG=xqt/recipes/smoke_cpu.yaml xqt-run-recipe
XQT_WRITE_MANIFEST=0 xqt-run-recipe
CLI

xqt-preflight

在真正执行前先做轻量检查. 它会检查 target 能不能 import, data root 在不在, 依赖包和可执行文件是否可用, CUDA 设备是否满足 recipe 要求, 最后输出 JSON.

XQT_CONFIG=xqt/recipes/image_vit_torchao_fp8.yaml xqt-preflight
API

xqt.run_xqt_recipe()

这是 Python 侧最核心的顶层入口. 它会装载 config, 创建 XQTContext, 构造 pass pipeline, 依次执行, 最后按需写出 manifest.

from xqt import run_xqt_recipe

context = run_xqt_recipe("xqt/recipes/smoke_cpu.yaml")
print(context.metrics)
print(context.artifacts)

四. 一条 recipe 是怎么跑起来的

XQT 的主链路并不复杂. 真正的骨架可以概括成 Config -> Context -> Pipeline -> Manifest.

1. load config
load_xqt_config
XQTConfig 2. create context
create_context
XQTContext 3. build pipeline
default_pass_names
SequentialPipeline 4. run passes
load_model
... -> write_reports 5. write outputs
metrics.*
manifest.json
1
xqt.core.config.load_xqt_config() 先用 OmegaConf.structured(XQTConfig) 建默认 schema, 再叠加 YAML 或 mapping 覆盖, 最后做几项最基础的校验, 比如 config_version, compression axes, benchmark 数值范围, prune/diffusion 参数合法性, 以及 export / ONNX QDQ 路径里的 pre_export_fusion 配置.
2
xqt.pipeline.runner.create_context() 把 config 包进一个可变的 XQTContext. 后面的 pass 都是在这个对象上读写 model, teacher, data, metrics, artifacts, manifest.
3
xqt.pipeline.runner.default_pass_names() 按默认顺序决定需要跑哪些 pass: load_model, load_data, baseline_eval, 然后按开关插入 distill, prune, quant, diffusion_distill, 可选 analyze, 最后是 export, benchmark, write_reports.
4
xqt.pipeline.pass_manager.SequentialPipeline 顺序执行每个 pass. 某个 pass 抛异常时, 它会被包成 XQTPipelineError; 每个成功执行的 pass 名称都会追加到 manifest 里.
5
xqt.core.artifact.ArtifactManifest 收集项目名, checksum, 配置快照, 依赖版本, 产物列表和指标列表. run_xqt_recipe() 默认会把它写到 artifact_dir/manifest.json.

五. recipe 到底长什么样

xqt/core/schema.py 定义的是一套很轻量的 schema. 它不是“魔法 DSL”, 本质上就是几层 dataclass: project, model, data, compression, export, validation, benchmark.

project

ProjectConfig 只有两个核心字段: name 和 artifact_dir. 一个 recipe 跑完后大多数产物都会归到这个目录下.

model

ModelConfig 继承自通用 ComponentConfig, 关键字段是 target, params, checkpoint, dtype, device. target 是一个 dotted import string.

data

按 split 分成 train, validation, calibration, prompts. 每个 split 都是 DataSplitConfig, 包含 target, root, sample_limit, batch_size, params.

compression

通过 axes 声明压缩维度, 再分别用 quant, prune, distill, diffusion_distill 四个子配置开关真实 pass.

export

export.targets 是一个列表, 每个元素是 ExportTargetConfig. 里面有 format, output_path, opset, precision, dynamic_shapes, profiles, params.

validation / benchmark

validation.output_diff 控制 runtime diff 阈值; validation.metric 控制任务指标容忍度; benchmark 控制 warmup, iterations, percentiles, CUDA 同步和是否测内存.

config_version: 1

project:
  name: xqt_smoke_cpu
  artifact_dir: artifacts/xqt/smoke_cpu

model:
  target: torch.nn.Linear
  params:
    in_features: 4
    out_features: 2
  device: cpu

data:
  validation:
    target: synthetic_classification
    sample_limit: 8
    batch_size: 2

compression:
  axes: [precision, sparsity]
  prune:
    enabled: true
    method: global_l1_unstructured
    target_sparsity: 0.5

export:
  targets:
    - format: torch_export
      output_path: artifacts/xqt/smoke_cpu/model.pt2

这个例子基本就是 xqt/recipes/smoke_cpu.yaml 的缩写版. 从它可以看出 XQT 的设计倾向: 尽量靠一份清晰的 YAML 把“目标模型是什么, 数据从哪来, 开哪些 pass, 输出写到哪”描述清楚.

六. 当前内置 pass 在做什么

真正的业务分支主要集中在 xqt/pipeline/passes.py. 如果想理解 XQT 现在“实际能跑到什么程度”, 这里比规划文档更重要.

Pass 类 主要行为
load_model LoadModelPass 根据 model.target 调 build_target() 实例化模型. 普通路径要求产物是 torch.nn.Module. 如果 target 返回的是 HFTextClassificationBundle, 它会顺便把 student, teacher, tokenizer 和 dataloader 塞进 context.
load_data LoadDataPass 当前内置只支持两类数据目标: synthetic_classification 和 torchvision_image_classification. 也就是说, 这条内置链路更偏 smoke 和通用视觉验证, 复杂数据一般靠你在调用 run_xqt_recipe() 时直接把 dataloader 注入 context.
baseline_eval BaselineEvalPass 调用 xqt.eval.evaluate_pytorch_model() 在 validation loader 上跑基线精度, 结果写到 context.metrics["baseline"] 和 manifest 指标里.
distill DistillPass 当前实现的是一个小型 teacher-student logit distillation loop. 它要求 context.teacher 和 train dataloader 已经准备好, 然后用 train_logit_distillation() 跑若干步并记录均值 loss.
prune PrunePass 内置剪枝主线目前是 global_l1_unstructured. 它既支持一次性剪枝, 也支持带 schedule 的 prune + KD loop, 最后会固化 reparameterization 并汇总稀疏率.
quant QuantPass 当前只支持两个 backend: torchao 和 onnxruntime_qdq. 前者直接在 PyTorch 模型上原地量化指定模块; 后者会先确保有 ONNX 图, 再做静态 QDQ 量化并把量化 ONNX 文件记到 artifact 里.
export ExportPass 按 export.targets 顺序导出. 目前能分支到 torch_export, torchscript, onnx, tensorrt, executorch, ncnn, mnn. 其中一些后端是纯 adapter 或 dry-run 命令生成器.
benchmark BenchmarkPass 取 validation 的第一个 batch 做延迟和可选内存基准, 底层用的是 xqt.benchmark.benchmark_callable() 和 benchmark_memory().
write_reports WriteReportsPass 把当前 context.metrics 写成 metrics.json 和 metrics.md. 这个 pass 不负责所有产物的导出, 它只负责把已经收集好的指标落盘.

七. 主要类和函数怎么用

这一节只讲那些“你真的可能直接 import 来用”的对象. 更深的内部 helper 可以读源码时再看.

config

XQTConfig 与 load_xqt_config()

XQTConfig 是 schema dataclass. load_xqt_config() 是最推荐的装载入口, 因为它会补默认值, 解析 OmegaConf resolver, 然后做基础校验.

from xqt import XQTConfig, load_xqt_config

config = load_xqt_config("xqt/recipes/smoke_cpu.yaml")
assert isinstance(config, XQTConfig)
print(config.project.artifact_dir)
runtime

XQTContext

这是所有 pass 共享的运行时容器. 你可以把它理解成“这次 recipe 执行的工作台”. 如果你不想完全依赖内置 data/model pass, 也可以先自己建好 model 或 dataloader 再塞进去.

from xqt.pipeline import create_context

context = create_context(
    "xqt/recipes/smoke_cpu.yaml",
    model=my_model,
    data={"validation": my_loader},
)
print(context.device)
runner

run_xqt_recipe()

最通用的执行入口. 它既能吃路径, 也能吃已加载好的 config. 你还可以传 model, teacher, data, 自定义 pass_names 或 pass_params.

from xqt import run_xqt_recipe

context = run_xqt_recipe(
    "xqt/recipes/prune_finetune_cpu.yaml",
    model=student,
    teacher=teacher,
    data={"train": train_loader, "validation": val_loader},
)
preflight

preflight_xqt_config()

适合在真正跑量化或导出前先做环境体检. 它返回的是 PreflightReport, 里面每条检查都是 PreflightCheck.

from xqt import preflight_xqt_config

report = preflight_xqt_config("xqt/recipes/image_vit_torchao_fp8.yaml")
print(report.passed)
print(report.to_dict())
artifact

ArtifactManifest

如果你想把 XQT 产物跟外部流程接起来, manifest 是最值得依赖的结构化对象. 它会记录配置快照, 依赖版本, checksum, 产物和指标.

from xqt import ArtifactManifest

manifest = ArtifactManifest(project_name="demo")
manifest.write_json("artifacts/demo/manifest.json")
xdl

XDL adapter

xdl_setup_to_xqt_context(), xdl_checkpoint_to_xqt_context(), load_checkpoint_into_model() 是 XQT 和 XDL 训练侧最关键的桥.

from xqt import xdl_setup_to_xqt_context

context = xdl_setup_to_xqt_context(
    setup,
    "xqt/recipes/smoke_cpu.yaml",
)

八. 各模块现在大概成熟到什么程度

下面这张表不是版本承诺, 只是帮助你快速判断“今天看哪个模块更值得投入时间”.

模块 当前角色 更适合怎么看
xqt.core 已经是主干. config, schema, registry, manifest, errors 都集中在这里. 如果你想理解 recipe 结构或想加一个新导出路径, 这里是第一站.
xqt.pipeline 已经是执行主骨架. runner, pass manager, 内置 passes, preflight 都是当前最真实的流程定义. 想知道“XQT 现在实际会做什么”, 优先读这个模块.
xqt.quant 当前最实用的压缩模块之一. 已经覆盖 torchao 和 ONNX Runtime QDQ 两条主线, 也有 calibration, policy 和 sensitivity helper. 如果你的目标是先落地一个量化闭环, 这里是最值得继续扩展的地方.
xqt.export 覆盖面很广, 但成熟度不完全一致. ONNX, torch export 较完整; TensorRT/OpenVINO/mobile 更偏 adapter 或命令封装. 看具体后端时要区分“完整导出 + 校验”和“外部工具 adapter”两种层次.
xqt.prune 已经有全局 L1 非结构化剪枝, 稀疏率汇总, 结构改写 helper 和 prune + KD schedule. 今天更像一个可用 baseline, 不是全套结构化剪枝系统.
xqt.distill 已经有 logit KD, feature/relation distillation loss, module hook, teacher cache, HF 文本分类 bundle 和小训练 loop. 如果你关心 teacher-student 流程怎么接 recipe, 这个模块已经有比较明确的骨架.
xqt.diffusion_distill 现在更像“扩散少步蒸馏的积木盒”: schedule, cache, loss, spec, report 都有, 但还不是一条完整 recipe 主链. 适合带着具体研究目标去读, 不适合作为现成闭环期待.
xqt.eval / xqt.benchmark 这两个模块很小, 但很关键. 它们负责把“有没有变快”“误差大不大”变成结构化报告. 读起来最轻, 也最容易拿去给外部流程复用.

九. 当前 recipe 地图

这些 YAML 基本代表了 XQT 现在已经打通或至少明确铺好的方向. 看 recipe 往往比看 README 更快知道今天能跑什么.

Recipe 想验证什么 实际意义
xqt/recipes/smoke_cpu.yaml 最小 CPU 闭环: schema, load_model, synthetic data, prune, torch export, manifest. 这是默认入口, 也是判断“基础 runner 还通不通”的第一份配方.
xqt/recipes/image_resnet_onnx_qdq_int8.yaml ResNet 类模型的 ONNX 导出, ONNX Runtime QDQ INT8, TensorRT dry-run. 这条 recipe 展示的是部署导向最强的那条路径: 先有 ONNX 图, 再量化, 再往 TensorRT 方向接.
xqt/recipes/image_resnet_cifar100_qdq_cpu.yaml 把上面的 ONNX QDQ 路径接到本地 CIFAR-100 数据上. 它比纯 synthetic smoke 更接近真实数据, 但仍偏验证性质.
xqt/recipes/image_vit_torchao_fp8.yaml ViT + torchao FP8 + CUDA benchmark. 这条 recipe 是早期 torchao_vit.py 实验向通用流水线收敛的直接体现.
xqt/recipes/prune_finetune_cpu.yaml 线性剪枝 schedule 和 teacher KD 微调组合. 它说明 XQT 的剪枝不是只做一次掩码, 而是已经开始考虑“剪完怎么恢复”.
xqt/recipes/hf_text_kd_prune.yaml HuggingFace 文本分类 teacher-student bundle + KD + pruning. 这条 recipe 证明 XQT 不只想做视觉部署, 也在尝试把 NLP 的蒸馏和剪枝流程 recipe 化.

十. 导出与后端边界

xqt/export/capability.py 已经把“有哪些导出格式, 优先级如何, 是否支持动态 shape, 是否支持量化”总结成能力矩阵. 这个模块很适合用来快速判断后端路线.

格式 状态 现在怎么看
torch_export implemented PyTorch 自家 ExportedProgram 路径, 是最轻量也最稳的内部导出基线之一.
onnx implemented 现在是很多后端的中间桥梁, 也是 QDQ 和 TensorRT/OpenVINO 适配最常见的入口.
tensorrt adapter 当前重点是 trtexec 命令构造, dry-run, engine 生成和性能阈值检查, 不是自己实现 TensorRT 编译器.
torchscript implemented 更像一个回退路径和兼容桥, 不是 XQT 当前最优先的部署主线.
openvino, executorch, ncnn, mnn adapter 这些更多是可选后端接入点. 在阅读时要把它们理解为“XQT 统一了入口和报告方式”, 而不是“XQT 完整接管了这些后端”. 
from xqt.export import deployment_capability_matrix

for capability in deployment_capability_matrix(implemented_only=True):
    print(capability.format, capability.status, capability.runtimes)

十一. XQT 与 XDL 的关系

XQT 的重要设计选择之一是“与 XDL 松耦合, 但不是断开关系”. 训练和压缩/部署不是两套完全平行的世界.

从 TrainSetup 接入

xdl_setup_to_xqt_context() 会把 XDL 的 train_loader, val_loader, 可选 test_loader, 以及 setup.model 打包成 XQT context. 对已经用 XDL 训练起来的项目很方便.

从 checkpoint 接入

load_checkpoint_into_model() 能处理几种常见 checkpoint 布局, 包括 model_state_dict, state_dict 和原始 state dict. xdl_checkpoint_to_xqt_context() 再把它包进 context, 同时保留 source checkpoint 追踪信息.

边界在哪里

XQT 不去接管 XDL 的训练生命周期. 它的职责是“接住训练结果, 继续往压缩, 导出, 验证走”. 所以如果你需要的是完整训练 loop, 还应该优先在 XDL 里解决.

十二. 建议的阅读顺序

如果你要真正改 XQT 或在它上面接自己的 recipe, 推荐按下面顺序读, 效率最高.

1

3

4

5

十四. 最后怎么概括 XQT

如果只用一句话概括当前 XQT, 可以这样理解: 它已经不是几个零散实验脚本, 但也还没到稳定公共子框架的阶段; 它最有价值的部分, 是已经把压缩与部署这条后处理链路收拢成了可配置, 可验证, 可落盘的一条 recipe 流水线.

今天最值得直接依赖的是顶层入口, recipe schema, runner, manifest, 以及几个已经较实用的量化/导出/评估 helper. 今天最需要保守对待的是子模块内部细节和具体实现形态, 因为这些仍在继续收敛.

事实源仍是 docs/md/XQT.md, docs/md/README.md 和 xqt/ 源码.
